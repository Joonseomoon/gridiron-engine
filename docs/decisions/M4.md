# M4 decisions: compare football decisions

## M4 shared prerequisite (draft, 2026-11-08)

**Status: agreed by both developers on 2026-11-08** (teams out of `GameState`, overtime in M4 with ties counted as half
a win, one policy per team, and the 4.1 split). Numbers are placeholders that M5 replaces with fitted values; the
structure is what has to last.

**The demo:** BAL trails SEA 24–27 with 3:14 left, 4th-and-2 at SEA's 43. Compare going for it, punting, and a field
goal by win probability, with uncertainty.

### Teams out of `GameState`

- **Decision:** `GameState` holds only the situation. Teams travel separately as `Matchup` (moved from the CLI to the
  engine).
- **Reason:** a scenario is then just a `GameState`, with no second type to keep in sync and nothing but plain fields for
  the M6 API to read. It touches three source files (`GameRunner`, `OutcomeSampler`, `GameLog`) and about 70 test lines,
  and M4 is about to add many more tests that build states.
- **Consequence:** done first, with no output change; the `m3-v1` fingerprints must still match. Resolves the
  `TASKS.md` item.

### Scenario

- **Decision:** a scenario is a `GameState` plus a `Matchup`. `GameState` gains `home_timeouts` and `away_timeouts`
  (default 3, reset at halftime). A validator returns every problem it finds: quarter 1–4, time 1–900, down 1–4, distance
  at least 1 and no more than the yards to the goal, ball position 1–99, timeouts 0–3, scores not negative.
- **Example:** home BAL, away SEA, `quarter` 4, `time_remaining_seconds` 194, `possession` Home, `down` 4, `distance` 2,
  `ball_position` 57, `home_score` 24, `away_score` 27, 3 timeouts each.
- **Decision (4.2 A):** `opening_possession` is not checked. It only decides the second-half kickoff, so it matters
  only for Q1–Q2 scenarios; callers starting there set it (default Home). The validator is separate from `resumeGame`:
  a scenario is checked once and then resumed many times.
- **Reason:** the M5 prediction time and M6 request can both be expressed as the same few fields.

### Outcomes and clock

```cpp
enum class PlayType { Run, Pass, FieldGoalAttempt, Punt };
enum class OutcomeType { Normal, Turnover, FieldGoalMade, Incomplete, Punted };

struct PlayOutcome {
    PlayType play_type;
    OutcomeType outcome_type;
    int yards_gained = 0;       // For a punt: net yards, including any return.
    int elapsed_seconds = 0;    // Time the play itself takes.
    int runoff_seconds = 0;     // Time until the next snap, removed if the clock stops.
    bool out_of_bounds = false;
};
```

- **Decision:** the clock stops, removing the runoff, on an incomplete pass, a timeout, the two-minute warning, and out of
  bounds in the last 2:00 of Q2 and last 5:00 of Q4. Following the NFL, it also stops after any score or change of
  possession (turnover, turnover on downs, punt), added in 4.1 A. Today's sampled play time becomes `elapsed_seconds` of a fixed 6 plus
  the remainder as runoff.
- **Decision:** a punt moves the ball by net yards and changes possession at the spot; past the goal line it is a
  touchback at the 20 (NFL rule; corrected from the 25 in 4.1 A). A net that reaches the punting team's own goal line is
  a return touchdown. No blocks or separate returns.
- **Decision:** passes are incomplete at a flat rate, about 35% to start, and yardage is sampled only for completions.
- **Reason:** these outcomes exist in play-by-play data, so M5 can fit them without changing the structure.
- **Consequence:** `maximumPlays` in `GameRunner.cpp` assumes 10 seconds per play and must use the new minimum of 6, or
  valid games would throw. All new numbers are named constants in one place. No parameter loader yet: that is M5.3.
- **Out of scope:** hurry-up pace, penalties, two-point tries, kickoffs and returns, playoff overtime.

### Overtime

- **Decision:** regular-season rules. A game tied after Q4 plays one 10-minute period (`quarter` 5, 600 seconds). A coin
  toss picks who receives at the kickoff spot. Both teams are guaranteed a possession, subject to the clock; once both
  have had one, the leader wins, and if still tied the next score wins. If time expires tied, the game is a tie. A
  defensive score on the first possession ends the game.
- **Decision:** `GameState` gains `overtime_possessions_completed`. Each team has 2 timeouts in overtime (confirmed at
  the 4.1 checkpoint, below).
- **Reason:** trailing by 3, a made field goal ties the game, so the value of that option depends on what happens next.
- **Consequence:** lands after the policy extraction has left the fingerprints unchanged, and before `m4-v1`. Keep the
  logic in its own function, because `applyOutcomeInPlace` is shared with the 4.1 rules work. `maximumPlays` must include
  the overtime period, and the invariant sweep's "no 5th quarter" check changes. Scenarios start in regulation only.

### Policy

```cpp
class Policy {
public:
    virtual ~Policy() = default;
    virtual PlayType choosePlay(const GameState& state, const Matchup& teams, RandomSource& random) const = 0;
    // Asked after the play is sampled, only when the clock would keep running and the team has a timeout left.
    virtual bool callTimeout(const GameState& before, const PlayOutcome& outcome, Possession team) const = 0;
};

struct Policies {
    const Policy& home;
    const Policy& away;
};
```

- **Decision:** one policy per team, so 4.3 can compare a conservative team against an aggressive one. `const` and
  stateless, with all randomness through `RandomSource`, so one policy can be shared across threads.
- **Decision:** the default policy first copies today's behavior exactly, keeping the draw order, so `main`'s
  fingerprints are the same before and after. Only then, at the 4.1 checkpoint, does it start punting (4th down,
  outside field goal range, unless the distance is short).
- **Reason:** the fingerprint proves the extraction changed nothing. M5 can then add a fitted play-calling policy without
  touching the engine.
- **Consequence:** one indirect call per play decision; benchmark at 1 and 10 threads against the M3 results.

### Candidate actions and resuming

```cpp
enum class CandidateAction { GoForIt, Run, Pass, Punt, FieldGoal };

GameState resumeGame(GameState start, const Matchup& teams, const Policies& policies,
                     std::optional<CandidateAction> firstAction, std::mt19937& rng,
                     const PlayObserver& onPlay = {});
```

- **Decision:** the action applies to the first play only, and policies decide everything after it. `GoForIt` picks run
  or pass with the default 50/50 draw (`chooseRunOrPass`, shared with `DefaultPolicy`); `Run` and `Pass` force the play.
  Any down is allowed (widened from 4th down only in 4.2 A). Run-versus-pass comparisons only become meaningful once M5
  fits the yardage.
- **Decision:** `onPlay` lets the CLI print a resumed game; it draws no random numbers.
- **Decision:** `runGame` becomes the coin toss followed by the same loop, so there is one game loop.

### Comparison result

- **Decision:** results are from the perspective of the team deciding. For each action: games, wins, ties, and win value
  (`P(win) + 0.5 × P(tie)`, since a regular-season game can still end tied after overtime). For each pair of actions: the difference in win value and its 95%
  CI. The runner lives in `gridiron_core` and returns a struct, so the M6 API can use it; the CLI only prints it.
- **Decision:** every action uses the same seeds (`batchSeed + i`), and the CI comes from the per-game paired differences.
- **Reason:** the paired CI is valid whether or not the shared seeds reduce noise. Games diverge once actions draw
  different numbers, so 4.3 measures whether pairing helps.

### Model version and checks

- **Decision:** the 4.1 checkpoint bumps to `m4-v1` and records new fingerprints. Games change on purpose, so the M3
  "statistics unchanged" check does not apply.
- **Sanity check (rough, by hand):** about 20–25 points per team per game, 3–5 punts per team per game, about 60–65%
  completions, tie rate well below today's 2.6%, and every game finishing. Retune the hand-set constants if these are far
  off. This includes field goals: today's linear formula gives a 60-yard kick 55% with a 0.95 rating.

### Decided later

- **Start of 4.3:** whether the M4 command is a new `simulate` mode or a separate program, and how a scenario is entered.

## 4.1 checkpoint (2026-11-17)

### Rules verified

Checked against the [2026 NFL Official Playing Rules](https://media.nfl.com/content/dam/communications/Official%20Playing%20Rules/2026%20Official%20Playing%20Rules.pdf)
(Rules 16-1-3, 16-1-5, 4-3-2, 4-4):

- Regular-season overtime is one 10-minute period with 2 timeouts per team. Q4 timing rules apply, including the
  two-minute warning and the late out-of-bounds rule.
- A safety or defensive return touchdown on the opening possession ends the game. An opening touchdown or field goal
  allows a reply: a tying reply continues, and a failed or go-ahead reply ends the game.
- Still out of scope: penalties, extra-point and two-point tries (touchdowns are 7), playoff overtime.

`startOvertime` and `finishOvertimePlay` handle overtime setup and how it ends; clock expiry stays in
`applyOutcomeInPlace`. A finished overtime game stays at quarter 5.

### Default policy and spots

- **4th down:** field goal within 40 yards of the goal line; outside it, go for it with 1–2 yards to gain
  (`kFourthDownGoForItMaxDistance`), otherwise punt. Choosing a punt draws no random number.
- **Timeouts:** a trailing team calls one after a play that leaves 1–120 seconds in Q2, Q4, or overtime
  (`kTimeoutWindowSeconds`). This is a simple starting strategy, not an optimized one. The engine asks only eligible
  teams, offense first, and charges at most one timeout per play. A timeout removes runoff, never the snap. Three per
  half; overtime starts with two.
- **Spots:** kickoffs (opening, halftime, after scores, overtime) start at the receiving team's 35; punt and turnover
  touchbacks at the 20.

## 4.2 B late-game policy

**Fourth down.** With 2:00 or less left in Q4, an offense facing fourth down within 40 yards of the goal line
goes for it when trailing by four or more. A made field goal would still leave the offense behind, and it may
never get another possession. Down three at the same spot, the offense kicks because a field goal can tie the game.
Outside field-goal range, a trailing offense goes for it at any deficit instead of punting (fixed in 4.3 A).
Going for it uses the shared `chooseRunOrPass` draw with the game's `RandomSource`. All other play calls use
`DefaultPolicy`.

**Timeouts.** In Q4, a trailing defense requests an eligible timeout with 1–120 seconds left after the play.
The opponent controls the next snap and can run down the clock. A trailing offense controls its own snap timing,
so it saves its timeouts until 1–60 seconds remain. Both windows include their endpoints. A team that is tied
or ahead declines the timeout in Q4. Other quarters, including overtime, use the default timeout rule.

**Checkpoint.** BAL trails SEA 24–27 with 3:14 left in Q4, facing fourth-and-2 at SEA's 43.
`IntegrationTest.ResumeExampleScenarioUnderTwoActions` assigns `LateGamePolicy` to both teams so both respond
to the clock and score under the same rules. Only BAL's forced opening decision changes between batches.
Using seeds 1000–1999 for each action, all 2,000 games finished. BAL's average win value was 0.378 after
`GoForIt` and 0.226 after `FieldGoal` (4.2 B values 0.3755 and 0.221, before the 4.3 A punting fix), counting a
win as 1, a tie as 0.5, and a loss as 0.

## 4.3 A policy variants

Two continuation policies bound how much the play calls after the first play can move the recommendation. Both
change only 4th-down calls and use `LateGamePolicy`'s timeout rules, so any difference between them comes from 4th
down, not clock management. Each holds a `LateGamePolicy` member rather than inheriting from it.

**`ConservativePolicy`.** Every 4th down is a kick: a field goal within 40 yards of the goal line, a punt otherwise, at
any score or time. Downs 1–3 use the shared `chooseRunOrPass` draw.

**`AggressivePolicy`.** In Q4 with 5:00 or less left (`kAggressiveWindowSeconds`), an offense that is not leading goes
for it on 4th and 4 or shorter (`kAggressiveMaxDistance`). All other calls follow `LateGamePolicy`.

## 4.3 A sensitivity results

The M4.md example (BAL 24–27, 3:14 left in Q4, 4th and 2 at SEA's 43) under each forced first action. Each cell is
BAL's win value over 1,000 games with seeds 1000–1999, the same seeds for every action
(`tests/integration/policy_sensitivity_test.cpp`). With 1,000 games a cell's 95% CI is roughly ±0.03; 4.3 B's runner gives
proper paired CIs for the differences.

**Continuation policies** (BAL v SEA, for every play after the first):

| BAL v SEA | GoForIt | FieldGoal | Punt |
|---|---|---|---|
| Default v Default | 0.380 | 0.211 | 0.164 |
| LateGame v LateGame | 0.378 | 0.226 | 0.175 |
| Conservative v Conservative | 0.381 | 0.230 | 0.166 |
| Aggressive v Aggressive | 0.404 | 0.240 | 0.177 |
| Aggressive v Conservative | 0.401 | 0.233 | 0.167 |
| Conservative v Aggressive | 0.382 | 0.231 | 0.174 |

**Input: BAL's `field_goal_rating`** (both teams `LateGamePolicy`). The kick from SEA's 43 is 60 yards, so the make
chance is `rating − 0.40`.

| Rating | 60-yard make chance | GoForIt | FieldGoal | Punt |
|---|---|---|---|---|
| 0.6 | 20% | 0.353 | 0.155 | 0.164 |
| 0.8 (default) | 40% | 0.378 | 0.226 | 0.175 |
| 1.0 | 60% | 0.398 | 0.302 | 0.183 |

**Conclusion.** Going for it is best in every case, by 0.15–0.17 over the field goal across policies and by at least
0.10 even with a 60% make chance from 60 yards. The continuation policies move the values by at most about 0.03, so
the recommendation does not depend on them. The kicker rating narrows the gap but does not flip it; at 0.6 the field
goal drops below the punt.

## 4.3 compareActions interface (proposed by A, for B to adjust)

```cpp
// Results are from the perspective of the team with the ball in `start`.
struct ActionResult {
    CandidateAction action;
    int games = 0;
    int wins = 0;
    int ties = 0;
    double win_value = 0.0; // (wins + 0.5 × ties) / games
};

struct ActionDifference {
    CandidateAction first;
    CandidateAction second;
    double win_value_difference = 0.0; // first − second
    double ci95 = 0.0;                  // half-width, from the per-game paired differences
};

struct ActionComparison {
    std::vector<ActionResult> actions;          // in input order
    std::vector<ActionDifference> differences;  // every pair i < j, in input order
};

ActionComparison compareActions(const GameState& start, const Matchup& matchup, const Policies& policies,
                                const std::vector<CandidateAction>& actions, int games, std::uint32_t batchSeed,
                                int threads = 1);
```

- Game `i` of every action uses seed `batchSeed + i`, so results match `balWinValue` in the 4.3 A test and are the
  same at every thread count.
- Throws `std::invalid_argument` if `validateScenario(start)` reports problems, `actions` is empty or has duplicates,
  or `games < 2` (a CI needs two games).
- Policies are shared across threads, so they must not hold mutable state. All four current policies are stateless.
