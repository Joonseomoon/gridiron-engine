# M4 decisions: compare football decisions

## M4 shared prerequisite (draft, 2026-11-08)

**Status: agreed by both developers on 2026-11-08** (teams out of `GameState`, overtime in M4 with ties counted as half
a win, one policy per team, and the 4.1 split). Numbers are placeholders that M5 replaces with fitted values; the
structure is what has to last.

**The demo:** BAL trails SEA 24–27 with 3:14 left, 4th-and-2 at SEA's 43. Compare going for it, punting, and a field
goal by win probability, with uncertainty.

### Teams out of `GameState`

- **Decision:** `GameState` holds only the situation. Teams travel separately as `Matchup` (moved from the CLI to the
  engine).
- **Reason:** a scenario is then just a `GameState`, with no second type to keep in sync and nothing but plain fields for
  the M6 API to read. It touches three source files (`GameRunner`, `OutcomeSampler`, `GameLog`) and about 70 test lines,
  and M4 is about to add many more tests that build states.
- **Consequence:** done first, with no output change; the `m3-v1` fingerprints must still match. Resolves the
  `TASKS.md` item.

### Scenario

- **Decision:** a scenario is a `GameState` plus a `Matchup`. `GameState` gains `home_timeouts` and `away_timeouts`
  (default 3, reset at halftime). A validator returns every problem it finds: quarter 1–4, time 1–900, down 1–4, distance
  at least 1 and no more than the yards to the goal, ball position 1–99, timeouts 0–3, scores not negative.
- **Example:** home BAL, away SEA, `quarter` 4, `time_remaining_seconds` 194, `possession` Home, `down` 4, `distance` 2,
  `ball_position` 57, `home_score` 24, `away_score` 27, 3 timeouts each.
- **Reason:** the M5 prediction time and M6 request can both be expressed as the same few fields.

### Outcomes and clock

```cpp
enum class PlayType { Run, Pass, FieldGoalAttempt, Punt };
enum class OutcomeType { Normal, Turnover, FieldGoalMade, Incomplete, Punted };

struct PlayOutcome {
    PlayType play_type;
    OutcomeType outcome_type;
    int yards_gained = 0;       // For a punt: net yards, including any return.
    int elapsed_seconds = 0;    // Time the play itself takes.
    int runoff_seconds = 0;     // Time until the next snap, removed if the clock stops.
    bool out_of_bounds = false;
};
```

- **Decision:** the clock stops, removing the runoff, on an incomplete pass, a timeout, the two-minute warning, and out of
  bounds in the last 2:00 of Q2 and last 5:00 of Q4. Today's sampled play time becomes `elapsed_seconds` of a fixed 6 plus
  the remainder as runoff.
- **Decision:** a punt moves the ball by net yards and changes possession at the spot; past the goal line it is a
  touchback at the 25. No blocks or separate returns.
- **Decision:** passes are incomplete at a flat rate, about 35% to start, and yardage is sampled only for completions.
- **Reason:** these outcomes exist in play-by-play data, so M5 can fit them without changing the structure.
- **Consequence:** `maximumPlays` in `GameRunner.cpp` assumes 10 seconds per play and must use the new minimum of 6, or
  valid games would throw. All new numbers are named constants in one place. No parameter loader yet: that is M5.3.
- **Out of scope:** hurry-up pace, penalties, two-point tries, kickoffs and returns, playoff overtime.

### Overtime

- **Decision:** regular-season rules. A game tied after Q4 plays one 10-minute period (`quarter` 5, 600 seconds). A coin
  toss picks who receives at the 25. Both teams are guaranteed a possession, subject to the clock; once both have had
  one, the leader wins, and if still tied the next score wins. If time expires tied, the game is a tie. A defensive score
  on the first possession ends the game.
- **Decision:** `GameState` gains `overtime_possessions_completed`. Each team has 2 timeouts in overtime. Confirm the
  timeout count and the defensive-score rule against the current NFL rulebook when implementing.
- **Reason:** trailing by 3, a made field goal ties the game, so the value of that option depends on what happens next.
- **Consequence:** lands after the policy extraction has left the fingerprints unchanged, and before `m4-v1`. Keep the
  logic in its own function, because `applyOutcomeInPlace` is shared with the 4.1 rules work. `maximumPlays` must include
  the overtime period, and the invariant sweep's "no 5th quarter" check changes. Scenarios start in regulation only.

### Policy

```cpp
class Policy {
public:
    virtual ~Policy() = default;
    virtual PlayType choosePlay(const GameState& state, const Matchup& teams, RandomSource& random) const = 0;
    // Asked after the play is sampled, only when the clock would keep running and the team has a timeout left.
    virtual bool callTimeout(const GameState& before, const PlayOutcome& outcome, Possession team) const = 0;
};

struct Policies {
    const Policy& home;
    const Policy& away;
};
```

- **Decision:** one policy per team, so 4.3 can compare a conservative team against an aggressive one. `const` and
  stateless, with all randomness through `RandomSource`, so one policy can be shared across threads.
- **Decision:** the default policy first copies today's behavior exactly, keeping the draw order, so `main`'s fingerprints are the same before and after. Only then, at the 4.1 checkpoint, does it start punting (4th down, outside field goal range, unless the
  distance is short).
- **Reason:** the fingerprint proves the extraction changed nothing. M5 can then add a fitted play-calling policy without
  touching the engine.
- **Consequence:** one indirect call per play decision; benchmark at 1 and 10 threads against the M3 results.

### Candidate actions and resuming

```cpp
enum class CandidateAction { GoForIt, Punt, FieldGoal };

GameState resumeGame(GameState start, const Matchup& teams, const Policies& policies,
                     std::optional<CandidateAction> firstAction, std::mt19937& rng);
```

- **Decision:** the action applies to the first play only, and policies decide everything after it. `GoForIt` picks run
  or pass with the default 50/50 draw. M4 covers 4th-down decisions only.
- **Decision:** `runGame` becomes the coin toss followed by the same loop, so there is one game loop.

### Comparison result

- **Decision:** results are from the perspective of the team deciding. For each action: games, wins, ties, and win value
  (`P(win) + 0.5 × P(tie)`, since a regular-season game can still end tied after overtime). For each pair of actions: the difference in win value and its 95%
  CI. The runner lives in `gridiron_core` and returns a struct, so the M6 API can use it; the CLI only prints it.
- **Decision:** every action uses the same seeds (`batchSeed + i`), and the CI comes from the per-game paired differences.
- **Reason:** the paired CI is valid whether or not the shared seeds reduce noise. Games diverge once actions draw
  different numbers, so 4.3 measures whether pairing helps.

### Model version and checks

- **Decision:** the 4.1 checkpoint bumps to `m4-v1` and records new fingerprints. Games change on purpose, so the M3
  "statistics unchanged" check does not apply.
- **Sanity check (rough, by hand):** about 20–25 points per team per game, 3–5 punts per team per game, about 60–65%
  completions, tie rate well below today's 2.6%, and every game finishing. Retune the hand-set constants if these are far
  off. This includes field goals: today's linear formula gives a 60-yard kick 55% with a 0.95 rating.
