Date: 2026-11-07  
Owner: Developer B (Austin)

## Goal and implementation

Speed up batch simulation without changing football rules, random draws, or output.
Previously, `applyOutcome` copied the entire `GameState` into a `PlayResult`, and
`runGame` copied the updated state back on every play. Each state includes both
team profiles and their names.

The new `applyOutcomeInPlace(GameState&, const PlayOutcome&)` updates the caller's
state directly and returns a `PlaySummary` containing only the event, turnover,
and period information. The football rules and clock logic live in this function.

The existing `applyOutcome` remains a compatibility wrapper: it copies its input,
updates that copy through the new function, and returns a `PlayResult`. Its input
remains unchanged. A distinct function name avoids changing overload resolution
for existing callers passing mutable states.

`runGame` now uses the in-place function. Without an observer, there are no
per-play `GameState` copies. With an observer, it saves the before-state and
constructs an after-state `PlayResult` so the existing observer interface and
play-by-play log still work. Game setup and observer snapshots still copy state.

`runGame` and `runBatch` signatures are unchanged. `BatchRunner.cpp` is unchanged;
Developer A's scheduling work is outside this change. The model remains `m3-v1`.

## One-thread benchmark

Machine: Apple M1 Pro, 16 GiB RAM, 8 CPU cores; macOS 27.2;
Apple Clang 21.0.0 (clang-2100.4.1.1).

Method follows [M3.md](M3.md): Release build, BAL versus SEA, 1,000,000 games,
seed 1000, one thread (the default), output discarded, one warm-up followed by
seven measurements with `/usr/bin/time -p`. Values below are elapsed `real`
seconds supplied by Austin. The fresh before measurements were collected after
the after measurements, using the saved original executable from revision
`71c1f7a`. The after measurements use the working-tree implementation.

| Run | Before (s) | After (s) |
| --- | ---: | ---: |
| 1 | 16.67 | 14.72 |
| 2 | 16.58 | 14.64 |
| 3 | 16.58 | 14.84 |
| 4 | 16.58 | 14.72 |
| 5 | 16.59 | 14.65 |
| 6 | 16.74 | 14.64 |
| 7 | 16.60 | 14.72 |
| **Median** | **16.59** | **14.72** |
| Range | 16.58–16.74 | 14.64–14.84 |
| Games/second | 60,277 | 67,935 |

The change saves **1.87 seconds per million games**, or **11.3% of elapsed time**.
The speedup is **1.13×** (approximately 12.7% more games per second).

The measured ranges do not overlap, supporting an improvement larger than the
variation within these runs. These are sequential measurements on one machine;
they do not eliminate thermal or background-load effects. An earlier before
median was 17.06 seconds; the fresher 16.59-second measurement is used here.
The M5's original 12.30-second baseline is a different-machine result and is not
used to calculate this change's speedup.

To repeat the after measurement from the repository root:

```sh
# Warm-up (not recorded).
./build-release/simulate BAL SEA --games 1000000 --seed 1000 > /dev/null

# Seven recorded runs; use the median of the real values.
for i in {1..7}; do
    /usr/bin/time -p ./build-release/simulate BAL SEA \
        --games 1000000 --seed 1000 > /dev/null
done
```

The original executable for this session is `/tmp/gridiron-m32/simulate-before`.
The original play-by-play snapshot is `/tmp/gridiron-m32/play-before.txt`.
These are temporary local artifacts, not committed benchmark fixtures.
